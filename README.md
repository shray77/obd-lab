# OBD-Lab

Лаборатория автомобильной диагностики на **виртуальной CAN-шине**. Без машины, без адаптера, без денег: сканер и блок управления общаются настоящими кадрами OBD-II и UDS, только кадры идут внутри процесса, а не по проводам.

Задача проекта — проверить на практике главную гипотезу: **ценность не в том, чтобы стереть чек, а в том, чтобы объяснить, почему он горит, и решить, можно ли его стирать.**

Прежде чем строить, мы посмотрели, кто уже это делает: см. [docs/precedents.md](docs/precedents.md). Коротко — эмуляторы уже есть и получше нашего, общий справочник кодов есть и он бесплатный, а свободными остаются статус-логика, журнал, русская курируемая база и кейсы.

## Что показывает демо

```bat
python -m obd_lab.demo
```

Сценарий из 12 циклов зажигания: холодные пуски, слабый АКБ, разовая помеха на шине, заменённая деталь. Демо проходит путь:

1. **Читает** все коды вместе со статус-байтом и freeze frame.
2. **Строит журнал** по циклам и находит закономерность: «P0171 срабатывает только при минусе».
3. **Выдаёт вердикт** по механике статуса, а не по названию кода.
4. **Стирает** — и показывает, что вернулось, а что нет.
5. **Объясняет** каждую ошибку по своей базе знаний.

Ключевые сцены:

- `P0171` активна → инструмент говорит «не стирать как ложную», потому что монитор не проходит прямо сейчас.
- `P0420` историческая → «можно стирать».
- `P0455` помечена permanent → «стереть невозможно, сканер тут бессилен».
- После стирания `P0171` возвращается на первом же холодном пуске. Это и есть ответ на вопрос «а если просто стереть?».

## Что внутри

```
obd_lab/
  canbus.py     виртуальная шина: кадры, адресация, трассировка
  isotp.py      ISO-TP (ISO 15765-2): нарезка и сборка длинных сообщений
  obd.py        OBD-II (SAE J1979): коды DTC, PID-ы live-данных
  uds.py        UDS (ISO 14229): статус-байт DTC, чтение, стирание, VIN
  ecu.py        виртуальный ЭБУ: мониторы, жизненный цикл кодов
  scanner.py    сканер: то, что раньше было железной коробкой
  channel.py    канал связи: виртуальный, ELM327, что угодно дальше
  elm327.py     канал через реальный адаптер (COM-порт, socket://)
  live.py       живая диагностика: python -m obd_lab.live --port COM5
  journal.py    SQLite-журнал циклов и аналитика плавающих сбоев
  verdict.py    вердикт по статус-байту (механика)
  knowledge.py  база знаний: русская курируемая + справочник OBDex
  reference.py  чтение локальной копии OBDex (CC0)
  cli.py        поиск по коду из командной строки
  demo.py       сценарий из 12 циклов и разбор
data/
  dtc/          русская курируемая база: engine / emissions / electrical
  obdex.sqlite3 справочник 9 533 кодов (не в git, собирается импортом)
tools/
  import_obdex.py  сборка справочника OBDex в SQLite
docs/
  precedents.md    кто уже это делает и что из этого следует
  hardware.md      почему свой сканер не нужен и что покупать
tests/
  test_protocol.py
```

Разделение намеренное: **вердикт считается механически** (по битам статуса),
а **смысл берётся из базы знаний**. Поэтому база не влияет на безопасность
решения, а только дополняет его.

## База кодов

Два слоя, и это принципиально:

1. **Русская курируемая база** (`data/dtc/*.yaml`, 36 кодов) — наша работа:
   проверки, приоритеты причин, оговорки, привязка к реальным сценариям.
   Именно здесь появляется смысл, которого нет в справочниках.
2. **Справочник OBDex** (`data/obdex.sqlite3`, 9 533 кода) — внешний слой
   под CC0. Подключается, когда кода нет в русской базе, и честно помечается
   как англоязычный.

Собрать справочник:

```bat
python tools/import_obdex.py
```

Поиск по любому коду:

```bat
python -m obd_lab.cli P0016 --verdict AF
python -m obd_lab.cli --stats
```

Для кода из русской базы показывается разбор с проверками; для остальных —
запись OBDex. Это и есть практическая разница между «36 курируемыми кодами»
и «справочником на 9 533»: первое — наше, второе — фундамент, на который
можно опереться.

## Запуск

Нужен Python 3.11+ и PyYAML. `pyserial` — только для живого подключения
к адаптеру; демо и тесты работают без него.

```bat
python -m pip install -r requirements.txt
python -m obd_lab.demo
python -m unittest discover -s tests -v
```

Или коротко:

```bat
python run.py
```

Шоу-режим для наглядной демонстрации (поднимает виртуальную «машину»,
проводит сеанс диагностики и сохраняет отчёт; нужен установленный
ELM327-emulator, см. [docs/emulator.md](docs/emulator.md)):

```bat
python tools\show.py
```

## Как это связано с реальной машиной

Слой протоколов уже настоящий: ISO-TP, OBD-II, UDS — те же байты, что летают
по шине автомобиля. Заменён только транспорт, и он вынесен в один интерфейс:

```
Channel.request(payload) -> bytes
```

Реализации:

- `VirtualChannel` — поверх виртуальной шины (демо и тесты);
- `Elm327Channel` — поверх реального адаптера ELM327/vLinker/OBDLink по COM-порту.

```bat
python -m pip install pyserial
python -m obd_lab.live --port COM5
python -m obd_lab.live --port COM5 --clear
```

`ScanTool`, `Journal` и `KnowledgeBase` при этом не меняются. Смена адаптера —
смена одного класса, а не переписывание проекта.

Стек уже прогнан против чужой реализации стандарта — эмулятора ELM327 + ЭБУ
(сценарий `car`): детект протокола, MIL, блоки кодов в обоих форматах, VIN
через мультифрейм, fallback с UDS на OBD-режимы. Как поднять стенд и какие
особенности эмулятора наш код учитывает — [docs/emulator.md](docs/emulator.md).

Почему это важнее выбора железа — в [docs/hardware.md](docs/hardware.md):
свой сканер собирать не нужно, нужен купленный адаптер и своё ПО поверх него.

## Что упрощено (и это честно)

- ISO-TP ждёт Flow Control после First Frame (счётчик FC, block size, STmin),
  но только на виртуальной шине: паузы между кадрами там не нужны, шина
  синхронная. На CANable через python-can это уже рабочий транспорт.
- Виртуальный ЭБУ поддерживает один блок (двигатель) и один набор DID-ов.
- Freeze frame упрощён до фиксированного набора полей.
- Жизненный цикл DTC приближён к реальному, но не повторяет его побитово.
- `Permanent DTC` в модели уходит после 40 успешных циклов; в жизни порог зависит от монитора.

Всё это помечено в коде. Ни одна из упрощённых частей не меняет архитектуру.

## Как расширять

**Новый код в русскую базу.** Добавить запись в `data/dtc/engine.yaml` (или
`emissions.yaml`, `electrical.yaml`):

```yaml
P0300:
  title: "Случайные пропуски зажигания"
  systems: [двигатель, зажигание]
  meaning: "ЭБУ видит пропуски, но не может привязать их к конкретному цилиндру."
  causes:
    - title: "Свечи или катушки"
      weight: high
      check: "Поменять местами катушки, посмотреть, переедет ли пропуск."
```

Коды, которых нет в русской базе, автоматически ищутся в справочнике OBDex —
добавлять их вручную не нужно.

**Новый сценарий.** Добавить `Monitor` в `build_vehicle()` в `demo.py`:

```python
Monitor("P0300", "Пропуски", lambda c: c["rpm"] < 600, permanent=False)
```

**Новый транспорт.** Реализовать один метод `request(payload: bytes) -> bytes`
(см. `channel.py`) — `ScanTool`, журнал и база знаний заработают без изменений.

## Позиция проекта

- **Безопасность важнее кнопки.** Коды ABS, SRS и подушек не стираются «чтобы не горело». Инструмент предупреждает и ведёт журнал действий.
- **Экология.** Сброс readiness-мониторов перед техосмотром — не наша задача.
- **Честность.** Большинство «ложных» ошибок — настоящие. Продукт строится на объяснении, а не на удалении.
